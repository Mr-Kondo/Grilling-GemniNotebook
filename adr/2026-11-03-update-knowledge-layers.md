# 更新知識を実行スキルから分離する

- 状態: accepted（2026-11-03、評価案の実装指示と設計方式の確認に基づく）
- 関連: [Issue #4](https://github.com/Mr-Kondo/Grilling-GemniNotebook/issues/4)

## 仮説と調査

実行記録、原資料を参照する知識索引、実行手順を分ければ、履歴を失わずに実行用スキルを小さく保てる。WikiSkillの三層構造を参考にするが、論文の効果を本スキルの効果とは扱わない。

調査した既存スキルは grilling（短いfrontmatterと対話手順）、official-prompt-tailor（目的別の補助参照）、mece-cluster-advisor（更新時だけの知識参照）、japanese-readability-editor（原資料へ到達する任意索引）。トリガーは既存の「Use when」を維持し、通常実行の指示を増やさない。全文読込や自動更新は、追加コストを正当化する証拠がないため採らない。

## 要件とモデル

- `feedback/`: 匿名化した実行結果、評価入力・出力。Git追跡・配布対象外。配置の退避はソースリポジトリや撤去対象から独立した `~/.local/state/grilling-gemini-notebook/backups/` に置く。
- `knowledge/`: 少数の索引。対象版、根拠の場所、条件、反例、採否を記録する。原資料を複製せず、未確認事項を確定知識にしない。ソースリポジトリだけに置く。
- `SKILL.md`・`references/`・実行スクリプト: 通常実行に必要な配布物。知識索引は通常実行から参照しない。
- 更新提案はIssueと紐づける。候補変更を評価し、却下した変更は戻すが根拠と不採用理由は残す。

代替は、全資料をSKILL.mdに入れる方式（肥大化）、自動WikiSkillフレームワーク導入（未検証の費用・依存）、既存履歴だけを使う方式（最小負担）。既存履歴を正本とし、必要な索引だけ追加する。

## 成功指標・撤退条件

計画1は、配布ファイルのハッシュ一致、知識・ログの非配布、install/update/uninstallの隔離HOMEでの正常系・異常系テスト合格を成功条件にする。失敗時は実Macの更新に進まない。

計画2は、索引ごとに追跡可能な一次根拠と適用条件を持ち、参照が壊れていないことを確認する。根拠のないパターンは増やさない。

計画3の対象・固定条件・採否は比較実行前に別ADRで定める。索引の存在や構造テストだけで品質改善を主張しない。効果が不明なら任意の手動探索補助に留める。

## 非機能要件

新規外部依存なし（Python標準ライブラリと既存シェル）。既存MITライセンスを維持。Notebook原文・認証情報・個人情報は記録・公開しない。参考論文の本文・コードを複製しない。常駐処理・自動課金は追加しない。MarkdownとCLIのテキストで利用でき、色やGUIを必須にしない。

索引の維持は不具合修正の時間を消費するため、全履歴の再整理は行わない。環境間の配置互換性と、各ホストでの意味的な品質は別に検証する。

## 実装計画と検証

1. `README.md`に目的・機能・使い方、`references/update-workflow.md`に更新手順を書く。
2. `scripts/install.sh`の明示的配布リストを維持し、update/uninstall、交換前のバックアップ、失敗時復旧を実装する。
3. `tests/test_install.py`で隔離HOMEを使い、更新・撤去・非配布・バックアップ・所有権ガードを検証する。
4. 少数の`knowledge/`索引を別段階で追加する。
5. 比較評価後に採否を記録する。各段階を別PR・リリースとし、検証後に既存5配置を更新・照合し、今回の不要なバックアップとブランチを片付ける。

- [x] 配布・ライフサイクルテスト合格（隔離HOME、Bash 3.2、11件）
- [x] 知識索引の根拠検証（K001/K002は公開ソース・採否判断にリンクし、ローカル参照の存在とfeedback非参照を自動検証）
- [x] 比較結果と採否の記録（[限定比較](2026-11-03-index-comparison.md)。改善の証拠なし、任意索引を維持し自動接続しない）
- 各段階のレビュー・公開・Mac配置・後片付けの完了証拠は[Issue #4](https://github.com/Mr-Kondo/Grilling-GemniNotebook/issues/4)で追跡する。

## 計画1の検証記録

Gemini 4 Argon Mediumの静的レビューを2回実施。全配置の復旧、前提リンクの事前確認、frontmatter内の所有権判定、テスト補強、バックアップ先の整合を採用した。Bash 3.2の空配列展開もガードし、実機の11テストに合格。非UTF-8入力の表示改善は、現状で変更前に拒否するため見送った。ホストでの意味的品質・停電時の原子的復旧はこの検証の対象外。
