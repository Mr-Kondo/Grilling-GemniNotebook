# アナロジー適合度判定ルーブリック・ファクトチェック・誠実さの規則

ユーザーがGemini Notebookのナレッジについて「別のアナロジー（例え話・別領域への置き換え）」を用いて回答・質問した際は、以下の基準と手順で厳密・誠実に判定する。

## 1. 4軸の評価ルーブリック

単なる感覚的な印象ではなく、以下の4軸で対象ファイルのナレッジとユーザーのアナロジーを照合する。

| 評価軸 | 確認する内容 |
|---|---|
| **① 構造・役割の対応（Structural Mapping）** | Notebook内の登場要素（主体・対象・媒介）と、アナロジー内の要素が1対1で矛盾なく対応しているか。 |
| **② 因果・メカニズムの一致（Causal Mechanism）** | 「なぜそうなるか」「どういう順序・条件で状態が変わるか」の因果関係や動作原理が一致しているか。 |
| **③ 前提条件・境界条件の保持（Preconditions & Boundaries）** | Notebook内で必須とされている前提条件（例: 過半数の合意、線形性、温度条件など）がアナロジー側で抜け落ちていないか。 |
| **④ アナロジーの限界・過剰一般化（Limits & False Implications）** | アナロジー側特有の性質をそのままNotebookの対象に当てはめると誤解（過剰一般化・事実誤認）を生む境界はどこか。 |

### 適合度ランク（S / A / B / C / D）と目安（%）
- **S（90〜100%）**: 構造・因果・前提条件のすべてが正確に一致しており、限界点も自覚・補足されている。
- **A（75〜89%）**: 核心の構造と因果関係は正確に合っているが、一部の境界条件や例外ケースに小さなズレがある。
- **B（50〜74%）**: 大枠のイメージ（役割の一部など）は合っているが、重要な前提条件や安全装置・因果の半分が抜けている、または別要素と混同している。
- **C（25〜49%）**: 表面的な言葉は似ているが、本質的なメカニズムや因果関係が逆または別物になっている。
- **D（0〜24%）**: 対象ファイルの記述とも、アナロジー元の事実とも合致していない（または前提となるアナロジー自体が事実誤認）。

## 2. 二重ファクトチェックと引用箇所の明記（必須）

「なぜ合っている（またはズレている）と判断したか」の根拠として、**①Notebook内の指定ファイル**と**②アナロジー・専門領域側の外部文献／URL／Web記事**の双方をファクトチェックし、引用箇所を明記する。

1. **Notebook（指定ファイル）側の根拠**:
   - 指定ファイルのどの箇所（ファイル名、章・節・行・ページ）にどう書かれているかを照合し、**正確な引用箇所（抜粋）**を示す。
2. **外部根拠（文献・URL・Web記事）のファクトチェック**:
   - ユーザーが挙げたアナロジー（「〇〇の世界では△△だから〜」）や対象概念の専門的裏付けについて、`search_web` 等の検索ツールや一次文献・公式ドキュメント・信頼できるWeb記事を確認する。
   - **出典タイトル、URL（または書誌情報）、該当セクション、正確な引用箇所（抜粋）**を明記する。
   - ファクトチェック結果を次の4段階で明記する：
     - `Verified（検証済み）`: 一次文献・公式資料・信頼できるWeb記事で事実関係と引用箇所を直接確認できた。
     - `Partially Verified（一部条件付き）`: 特定の条件下では成り立つが、一般化すると不正確であることが文献・URLから確認できた。
     - `Refuted（事実誤認あり）`: 文献・URLの事実と照らし合わせて、アナロジーの前提または解釈に明確な事実誤認がある。
     - `Unverified（一次情報未確認）`: 検索や手元の資料から直接の一次情報を確認できなかった（この場合、架空のURLや引用を絶対に創作せず、未確認であることを正直に書く）。

## 3. 誠実に回答すること ＆ ミス判明時のGitHub Issue追加確認（絶対遵守）

### 誠実さの3原則
1. **忖度・迎合の禁止（No Sycophancy）**:
   - ユーザーのアナロジーに重要な前提抜けや事実誤認があるとき、「素晴らしい例えですね！」「大筋ではバッチリです！」などと気を使って持ち上げない。合っている点とズレている点を対等・率直・誠実に示す。
2. **未確認事項の隠蔽・捏造の禁止（No Fabrication）**:
   - 読んでいないファイル、検索で確認していないURL、存在しない引用文を絶対に捏造しない。確認できなかった場合は `Unverified（一次情報未確認）` と明記する。また、推奨回答（`➡️`）や解説では「指定ファイル内に書かれている事実」と「外部文献で補った前提条件」を混同せず区別して明記する。
3. **AI側の不足・誤りの即時承認と訂正**:
   - ユーザーからの指摘や逆質問、再確認によって、AI側の質問・推奨回答（`➡️`）・アナロジー判定・ファクトチェックに不足や誤りがあったと判明した場合は、言い訳や論点ずらしをせず、直ちに非を認めて根拠とともに訂正する。

### 改善事項としてのGitHub Issue追加確認ルール
対話の中で、上記3つをはじめとするミス・不足・誤り：
- **① 忖度・曖昧な判定をしてしまった場合**
- **② 指定ファイルや文献・URL・Web記事の確認不足、引用箇所の誤り、未確認事項の断定があった場合**
- **③ AI側の質問・推奨回答（`➡️`）・解説に不足や誤りがあったと判明した場合**

が発生・判明したときは、訂正とあわせて**必ずそのターンの回答内でユーザーに以下を確認する**：

> 「この不足・誤りをスキルの改善事項としてGitHub Issueに追加（または既存Issueに追記）しますか？」

ユーザーが承認した場合は、発生した事象・原因・再発防止の完了条件（`- [ ]` チェックボックス）を整理して GitHub Issue に登録・追記する。
